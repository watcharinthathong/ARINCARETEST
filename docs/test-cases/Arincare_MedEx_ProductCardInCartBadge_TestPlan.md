## 1. SCOPE & OBJECTIVES

### ขอบเขตที่ทดสอบ (In Scope)
1. **Cart Summary Popup** — เปิดเมื่อกด "ตะกร้าสินค้าของฉัน" (ไอคอนรถเข็นบน header)
   - จำนวนรายการในตะกร้า, เลขคำสั่งซื้อ, รายการสินค้า, จำนวน, ราคา, ยอดรวมทั้งหมด, ยอดรวมย่อย
   - ปุ่ม "ดูตะกร้าสินค้า" → นำไปหน้าตะกร้าเต็ม
   - Scroll ภายใน popup เมื่อรายการเยอะ
   - พฤติกรรมบนมือถือ: แตะครั้งที่ 1 = popup ครึ่งจอ, แตะครั้งที่ 2 (ที่ปุ่มเดิม) = ไปหน้าตะกร้าเต็ม
2. **In-Cart Badge บน Product Card** — ป้ายสีเขียว "อยู่ในตะกร้าแล้ว · N กล่อง" แสดงเมื่อสินค้านั้นถูกเพิ่มลงตะกร้าแล้ว
3. **ความสอดคล้องของสถานะ (state sync)** ระหว่าง: badge บนการ์ด ↔ popup ↔ ไอคอนตะกร้า (ตัวเลข badge มุมขวาบน) ↔ หน้าตะกร้าเต็ม

### ขอบเขตที่ยกเว้นรอบนี้ (Out of Scope)
- Checkout flow / การชำระเงินจริง (ทดสอบแยกใน suite อื่น)
- โปรโมชั่น/คูปองส่วนลดที่มีผลต่อราคา (นอกจากตรวจว่าตัวเลขที่ popup แสดงตรงกับหน้าตะกร้า)
- POS-v2 / Web-App ERP (feature นี้อยู่บน Med-Ex Marketplace เท่านั้น ตามภาพหน้าจอที่ได้รับ)

### เป้าหมาย
- Pass rate ≥ 95%, Critical bug = 0 ก่อนขึ้น production
- Badge/popup/cart ต้องแสดง**ยอดตรงกันเสมอ** ไม่มี race condition ที่ทำให้ตัวเลขไม่ตรงกัน (นี่คือความเสี่ยงหลักของฟีเจอร์นี้)

## 7. TEST SCENARIOS (สรุประดับ Scenario — รายละเอียดเต็มอยู่ใน Test Case ชุดถัดไป)

> ⚠️ **แก้ไข trigger (ยืนยันจริงบน staging 2026-09-07)**: Popup เปิดด้วย **hover เมาส์ไปที่ปุ่ม "ตะกร้าสินค้าของฉัน" (Desktop)** ไม่ใช่การคลิก — คลิกที่ปุ่มจะ navigate ตรงไปหน้าตะกร้าเต็มทันที (ไม่เปิด popup เลย) เคสด้านล่างที่เขียนว่า "กด" ให้อ่านเป็น "hover" บน Desktop

### 7.1 Cart Summary Popup
- TC-BADGE-P01: hover ที่ปุ่มตะกร้าเมื่อตะกร้าว่าง → แสดง empty state ที่เหมาะสม (ไม่ error/ไม่ค้าง)
- TC-BADGE-P02: hover ที่ปุ่มตะกร้าเมื่อมี 1 รายการ → ข้อมูลครบ (รายการ/จำนวน/ราคา/ยอดรวม) ตรงกับที่เพิ่มจริง — เลขคำสั่งซื้อเป็นค่า placeholder (ยืนยันแล้วในหัวข้อ 2 ข้อ 1) ตรวจแค่ว่า**แสดงและไม่เปลี่ยนกลางคัน**ระหว่าง hover ค้างไว้ ไม่ต้องตรวจ uniqueness/persistence
- TC-BADGE-P03: hover ที่ปุ่มตะกร้าเมื่อมีหลายรายการจากหลายร้านค้า/ผู้ผลิต → แสดงครบทุกรายการ ยอดรวมถูกต้อง
- TC-BADGE-P04: รายการในตะกร้าเยอะจนล้นพื้นที่ popup → มี scrollbar ภายใน popup, ปุ่ม "ดูตะกร้าสินค้า" และยอดรวมยังคงอยู่ (sticky footer)
- TC-BADGE-P05: กดปุ่ม "ดูตะกร้าสินค้า" ใน popup → นำไปหน้าตะกร้าเต็มถูกต้อง ข้อมูลตรงกับใน popup
- TC-BADGE-P06: เอาเมาส์ออกจากปุ่มตะกร้า/popup (ไม่ hover ค้าง) → popup ปิด ไม่กระทบสถานะตะกร้า
- TC-BADGE-P07 (Mobile): แตะไอคอนตะกร้าครั้งแรก → popup แสดงครึ่งจอ (มือถือไม่มี hover จึงใช้ tap แทน)
- TC-BADGE-P08 (Mobile): แตะปุ่มเดิมอีกครั้ง**เมื่อใดก็ได้**ตราบใด popup ครึ่งจอยังเปิดอยู่ (ทั้งแตะรัวทันที และเว้นช่วงหลายวินาที) → ต้องนำไปหน้าตะกร้าเต็มเสมอ (ยืนยันแล้วในหัวข้อ 2 ข้อ 5 — ไม่มี timeout จำกัด)
- TC-BADGE-P09: เพิ่ม/ลบ/แก้จำนวนสินค้าขณะ popup เปิดอยู่ (ถ้าทำได้) หรือปิด-เปิดใหม่ → popup อัปเดตค่าล่าสุดเสมอ ไม่ค้างค่าเก่า (cache)

### 7.2 In-Cart Badge บน Product Card
- TC-BADGE-C01: เพิ่มสินค้าลงตะกร้าครั้งแรก → badge สีเขียว "อยู่ในตะกร้าแล้ว · N กล่อง" ปรากฏทันทีบน card เดิม ไม่ต้อง refresh
- TC-BADGE-C02: ⚠️ **แก้ไขจาก premise เดิม (ยืนยันจริงบน staging 2026-09-07)**: เพิ่มสินค้าเดิมซ้ำด้วยจำนวนใหม่บนการ์ด → badge **แทนที่**เป็นจำนวนล่าสุดที่เลือก **ไม่ใช่บวกสะสม** (พฤติกรรมเดียวกับกฎเปลี่ยนหน่วยขายในข้อ 2 — "เพิ่มลงตะกร้า" ทุกครั้งคือการ "ตั้งค่า" ไม่ใช่ "บวกเพิ่ม") เช่น เพิ่ม 1 ก่อน แล้วตั้งจำนวน=2 แล้วกดเพิ่มอีกครั้ง → badge ต้องแสดง "2" ไม่ใช่ "3"
- TC-BADGE-C03: ลดจำนวนสินค้าจนเหลือ 0 หรือเอาออกจากตะกร้า (ผ่าน popup/หน้าตะกร้า) → badge หายไปจาก card ทันที
- TC-BADGE-C04: Refresh หน้า / เข้าใหม่จาก session เดิม → badge ยังคงแสดงถูกต้องตามสถานะตะกร้าจริง (ไม่ใช่ local state ที่หายไป)
- TC-BADGE-C05: สินค้าที่ไม่เคยเพิ่มลงตะกร้า → ไม่มี badge แสดง (regression check ไม่ให้ badge ขึ้นผิดใบ)
- TC-BADGE-C06: เพิ่มสินค้าด้วยหน่วย "กล่อง" ก่อน แล้วกลับมาเปลี่ยนเป็น "แผง" บนการ์ดเดิมแล้วกดเพิ่มอีกครั้ง → badge ต้อง**แทนที่เป็นหน่วย/จำนวนล่าสุด (แผง)** ไม่ใช่โชว์ทั้งสองหน่วยหรือบวกสะสมข้ามหน่วย (ยืนยันแล้วในหัวข้อ 2 ข้อ 2)
- TC-BADGE-C06B: หลังเปลี่ยนหน่วยแล้ว เปิด popup/หน้าตะกร้า → ต้องเห็น line เดียวด้วยหน่วยล่าสุด ไม่มี line ค้างของหน่วยเดิม
- TC-BADGE-C07: หน้ารายการสินค้ามีการแบ่งหน้า (pagination)/filter แล้วสินค้าเดิมโผล่มาอีกหน้า → badge แสดงตรงกันทุกจุดที่การ์ดนั้นปรากฏ

### 7.3 State Sync (Critical — R1)
- TC-BADGE-S01: เพิ่มสินค้า A จาก card → badge บน card A ขึ้น, ไอคอนตะกร้า (จำนวนรวม) ขึ้น, เปิด popup เห็นสินค้า A, เข้าหน้าตะกร้าเห็นสินค้า A — **ทั้ง 4 จุดต้องตรงกัน**
- TC-BADGE-S02: ลบสินค้า A จากหน้าตะกร้าเต็ม แล้วกลับมาหน้ารายการสินค้า → badge บน card A ต้องหายไปด้วย
- TC-BADGE-S03: แก้จำนวนสินค้าจากหน้าตะกร้าเต็ม → badge บน product card อัปเดตตามเมื่อกลับมาดู
- TC-BADGE-S04: เปิด 2 tab ด้วย user เดียวกัน เพิ่มสินค้าใน tab 1 → tab 2 **ไม่จำเป็นต้องอัปเดตทันที** (ยืนยันแล้วว่า sync เฉพาะตอน reload) แต่หลัง **reload tab 2** ต้องเห็นค่าล่าสุดตรงกับ tab 1 เสมอ
- TC-BADGE-S05: กด +/- จำนวนบน card รัวๆ (rapid click) → ยอดสุดท้ายใน badge/popup/ตะกร้าตรงกับค่าที่ควรจะเป็น ไม่มี race condition ทำเลขเพี้ยน

### 7.4 Edge Cases / Negative
- TC-BADGE-E01: สินค้าที่อยู่ในตะกร้าอยู่แล้วเปลี่ยนเป็น Out of Stock (เช่นเคส CITAZOL) → badge บน card และรายการใน popup ต้อง**คงค่าเดิมไว้เฉยๆ** ไม่ลบ ไม่ error ไม่ block (ยืนยันแล้วในหัวข้อ 2 ข้อ 4 — ถือว่าจองสิทธิ์แล้ว)
- TC-BADGE-E01B: จากเคส E01 ต่อไปยังหน้าตะกร้าแล้วกด "ชำระเงิน" → ระบบต้องคำนวณ/ตรวจ stock ใหม่ ณ จุดนี้ (out of scope ของ popup/badge แต่เป็น smoke case เชื่อมต่อที่ต้องมี เพื่อยืนยันว่าไม่ปล่อยให้สั่งซื้อสินค้าหมดสต็อกหลุดไปได้)
- TC-BADGE-E02: ตะกร้ามีสินค้าจากหลายคำสั่งซื้อ/หลาย order draft (ถ้ามี) → popup แสดงแยกหรือรวมถูกต้องตามออกแบบจริง
- TC-BADGE-E03: จำนวนสินค้าในตะกร้าเกิน stock คงเหลือ (ถ้าระบบอนุญาตให้เพิ่มได้) → popup/badge ไม่ error, มี warning ตามควร
- TC-BADGE-E04: Session หมดอายุ/ถูก logout ระหว่างมี badge ค้างอยู่ → login ใหม่แล้ว badge ต้องตรงกับตะกร้าจริงของ user นั้น ไม่ใช่ค่าที่ค้างจาก session ก่อน

### 7.5 Responsive / Cross-Device

### 🔴 พบเพิ่มเติมระหว่างเขียน automation (ยืนยันจริงบน staging)

1. **โปรโมชั่นบางตัวมี modal ยืนยันคั่นก่อนเพิ่มลงตะกร้าจริง** — "ยืนยันการเพิ่มสินค้าในรายการสั่งซื้อ" พร้อมปุ่ม "ยกเลิก"/"ตกลง" (พบกับ ACCIN-BP 5G. ที่มีโปรโมชั่น A+B) Test case ที่เกี่ยวข้องต้องรองรับทั้ง 2 กรณี (มี/ไม่มี modal) — **⚠️ ต้อง verify ผลจริงว่า modal ปิดแล้ว** (รอปุ่มหายไป) หลังคลิก "ตกลง" อย่าคลิกเฉยๆแล้วเดาว่าสำเร็จ เคยเจอว่าคลิกไม่ error แต่ modal ไม่ปิดจริง (โดยเฉพาะถ้าคลิกกลาง fade-in animation) เหลือ modal ค้าง intercept ปุ่มอื่นทั้งหน้าต่อเนื่อง
2. **ช่องค้นหาสินค้า (`#product-search`) ต้องคลิก suggestion แรกใน autocomplete dropdown — ห้ามใช้ปุ่ม "ค้นหา"** (ไอคอนแว่นขยาย ไม่มีข้อความ "ค้นหา" ที่ actionable บน mobile viewport ทำให้ locator ค้าง) และกด Enter ก็ไม่ trigger เช่นกัน — **ต้องรอ debounce ~1 วินาทีหลังพิมพ์ก่อนเช็ค dropdown** ไม่งั้น dropdown อาจยังโชว์ suggestion ของ query ก่อนหน้าค้างอยู่ (กดผิดสินค้าไปเงียบๆ โดยไม่มี error)
3. **🟠 พบข้อมูลซ้ำในแคตตาล็อกข้ามร้านค้า**: สินค้าชื่อ "PROSCAR 5 MG TABLETS 30'S" และ "TANSY ONE 1.5 MG TABLETS 1'S" ต่างก็มี **2 รายการ**ในระบบพร้อมกันจากคนละร้านค้า (ร้านหนึ่งมีสต็อกจริง อีกร้าน Out of Stock) — ค้นหาด้วยรหัส/ชื่อสินค้าอย่างเดียวมีความเสี่ยงได้ผลลัพธ์ผิดร้าน แก้โดยให้ `findProductBySearch()` ไล่ดูผลลัพธ์ทุกตัว ข้าม Out of Stock อัตโนมัติ และกรองด้วยชื่อที่คาดหวัง (expectedName) ช่วยเลือกตัวที่ถูกต้อง ควรแจ้ง Dev/PM ตรวจสอบข้อมูล master data ด้วย (อาจเป็นข้อมูลทดสอบเก่าที่ไม่ได้ลบ)
4. **cart เป็น server-side state ผูกกับบัญชีผู้ใช้ ไม่ใช่ session/browser** — ยืนยันจาก modal "การกู้ข้อมูลตะกร้าสินค้า" ที่เจอตอน login และจากการที่สินค้าที่เคยเพิ่มไว้ยังอยู่ข้ามการเปิด browser ใหม่/context ใหม่ — เทส automation ทุกตัวต้อง cleanup (ลบสินค้าที่เพิ่ม) หลังจบเทสเสมอ เพื่อไม่ pollute ตะกร้าจริงของบัญชีทดสอบที่ใช้ร่วมกัน (ทำแล้วผ่าน fixture `trackedProducts` ใน `tests/medex/fixtures.ts`)
5. **⚠️ Headless Chromium โดน nginx บล็อก (403 Forbidden) บน staging นี้** — รันได้เฉพาะ `headless: false` เท่านั้นระหว่างพัฒนา ต้องตรวจสอบว่า CI ปัจจุบันรัน headless หรือไม่ ถ้าใช่ suite นี้ (และอาจรวมถึง suite อื่นที่แตะ marketplace) อาจรันไม่ผ่านใน CI จนกว่าจะแก้ไข (เช่น whitelist User-Agent, ปรับ nginx, หรือรัน headed ผ่าน Xvfb)
6. `input[type="number"]` (จำนวนในหน้าตะกร้าเต็ม/บนการ์ด) — ค่าที่แสดงอยู่ใน `value` ไม่ใช่ text node จึงต้องเช็คด้วย `toHaveValue()`/`inputValue()` ไม่ใช่ `toContainText()` เวลาเขียนเทสใหม่
7. **PHP Debugbar (dev toolbar ของ staging เอง) ลอยอยู่ล่างจอทุกหน้า เคย intercept pointer events** — แก้โดยซ่อนด้วย CSS (`display:none`) ผ่าน `page.addInitScript()` ตั้งแต่ต้น แทนที่จะพยายามคลิกทะลุมันทุกจุด
8. **การ์ดสินค้าบนหน้า list/grid มี control ครบ (เลือกหน่วย/จำนวน/ปุ่มเพิ่ม) เฉพาะ Desktop เท่านั้น — Mobile ไม่มีเลย** ต้องแตะเข้าไปหน้ารายละเอียดสินค้าก่อนเสมอถึงจะเจอ control (คนละ component/selector กับการ์ด list สิ้นเชิง) `addToCart()` ใน Page Object ตรวจจับอัตโนมัติแล้วว่าจะใช้ flow ไหน
9. **ลำดับสินค้าบนหน้า grid หน้าแรก (`?page=1`) ต่างกันระหว่าง Desktop กับ Mobile viewport** — สินค้าตัวเดียวกันอาจไม่อยู่ตำแหน่งเดิม ห้าม lookup ด้วยตำแหน่ง/ลำดับการ์ดตรงๆ ข้าม device ให้ค้นหาด้วยรหัส/ชื่อแทนเสมอ

### 12.1 ที่มา — สรุป Logic การคำนวณราคาในหน้าตะกร้าสินค้า (ตามที่ผู้ใช้ส่งมา)

**ตัวอย่างอ้างอิง** (จาก screenshot: 2 รายการ A/B, ราคาต่อหน่วย 100 บาท จำนวน 10 หน่วยเท่ากัน, มีส่วนลดรายตัว, โปรโมชั่นท้ายบิล 10%, คูปอง -100):

```
ราคารวมสินค้า (ก่อนส่วนลดใดๆ)
   สินค้า A: 100 × 10 = 1,000
   สินค้า B: 100 × 10 = 1,000
   รวม = 2,000.00
        │
        ├── ส่วนลดสินค้ารายตัว (แสดงขีดฆ่าที่แต่ละแถว 1,000 → 900)
        │   A: -100, B: -100 → รวม -200.00
        ↓
   ยอดหลังส่วนลดสินค้ารายตัว = 1,800.00
        │
        ├── Promotion "ท้ายบิล 10%" คิดจากยอดหลังหักส่วนลดรายตัวแล้ว (ไม่ใช่จากยอดรวมดิบ)
        │   1,800 × 10% = -180.00
        ↓
   ยอดหลัง Promotion = 1,620.00
        │
        ├── Coupon (คูปองส่วนลด) หักหลัง Promotion เสมอ
        │   -100.00
        ↓
   ยอดสุทธิ (รวม VAT 7% แล้ว) = 1,520.00
```

**คอลัมน์ "ราคาหลังลด" ต่อบรรทัด** (จุดสำคัญที่สุดของฟีเจอร์นี้): ไม่ใช่แค่ราคาหลังหักส่วนลดรายตัว (900) แต่เป็น**ราคาสุดท้ายที่ปันส่วน (allocate) จากยอดสุทธิทั้งบิลกลับไปที่แต่ละบรรทัด** ตามสัดส่วน — ในตัวอย่างนี้ A และ B มูลค่าเท่ากัน จึงได้คนละ 760.00 (รวม 760+760 = 1,520.00 = ยอดสุทธิเป๊ะ) **ผลรวมของคอลัมน์ "ราคาหลังลด" ทุกบรรทัด ต้องเท่ากับยอดสุทธิทั้งบิลเสมอ**

**ลำดับแสดงผล Summary ท้ายบิล** (ลำดับใหม่ที่ต้องการ):
```
ราคารวม              2,000.00
ส่วนลดโปรโมชั่น        -380.00   ← รวมส่วนลดรายตัว (200) + Promotion (180) เข้าด้วยกันเป็นตัวเลขเดียว
คูปองส่วนลด            -100.00
ค่าส่ง                    0.00
ราคาก่อนภาษี          1,420.56
ภาษี                      99.44
ยอดสุทธิ              1,520.00
```

**VAT**: ยอดสุทธิ (1,520.00) คือยอดที่ **รวม VAT 7% แล้ว** → ราคาก่อนภาษี = ยอดสุทธิ ÷ 1.07 = 1,420.56, ภาษี = ยอดสุทธิ − ราคาก่อนภาษี = 99.44 (ผลรวม 1,420.56 + 99.44 ต้อง = 1,520.00 เป๊ะ ไม่มีเศษสตางค์ตกหล่นจากการปัดเศษ)

**สรุป Logic สั้น**: `ราคาสินค้า → ส่วนลดสินค้ารายตัว → Promotion → Coupon → ยอดสุทธิ → แยกยอดก่อน VAT และ VAT 7%` — ส่วนการ**แสดงผล**ที่ Summary รวมส่วนลดรายตัวกับ Promotion เข้าด้วยกันเป็นบรรทัดเดียว "ส่วนลดโปรโมชั่น" แม้จะคำนวณคนละขั้นตอนกันก็ตาม

### 12.2 Scope

**In Scope**:
1. ความถูกต้องของการคำนวณราคาทุกขั้นตอน (รายตัว → Promotion → Coupon → VAT)
2. คอลัมน์ "ราคาหลังลด" ต่อบรรทัด ต้องปันส่วนจากยอดสุทธิถูกต้อง (ไม่ใช่แค่ส่วนลดรายตัว)

4. การคำนวณใหม่แบบ real-time เมื่อผู้ใช้แก้จำนวนสินค้า หรือลบคูปองออก

**Out of Scope รอบนี้**:

### 12.4 Test Scenarios

- **TC-CARTPRICE-001** (Critical): ราคารวมสินค้าก่อนส่วนลด = Σ(ราคาต่อหน่วย × จำนวน) ทุกบรรทัด — Test Data: A=100×10, B=100×10 → คาดหวัง 2,000.00
- **TC-CARTPRICE-002** (High): ส่วนลดสินค้ารายตัวแสดงถูกต้องต่อบรรทัด (ราคาเดิมขีดฆ่า + ราคาใหม่) — Test Data: 1,000→900 ต่อบรรทัด
- **TC-CARTPRICE-003** (Critical): คอลัมน์ "ราคาหลังลด" ต่อบรรทัด = ยอดสุทธิทั้งบิลปันส่วนตามสัดส่วนมูลค่าแต่ละบรรทัด ไม่ใช่แค่ส่วนลดรายตัว — ตรวจ Σ ราคาหลังลดทุกบรรทัด = ยอดสุทธิ (1,520.00) เป๊ะ
- **TC-CARTPRICE-004** (Critical): Promotion "ท้ายบิล 10%" คำนวณจากยอดหลังหักส่วนลดรายตัว (1,800) ไม่ใช่ยอดรวมดิบ (2,000) → คาดหวัง -180.00 ไม่ใช่ -200.00
- **TC-CARTPRICE-005** (High): Summary "ส่วนลดโปรโมชั่น" = ส่วนลดรายตัวรวม (200) + Promotion (180) = 380.00 (รวมเป็นบรรทัดเดียว)
- **TC-CARTPRICE-006** (High): หัก Coupon (-100) หลัง Promotion แล้วเสมอ → ยอดหลัง Promotion (1,620) − 100 = 1,520.00
- **TC-CARTPRICE-007** (High): VAT breakdown — ราคาก่อนภาษี = ยอดสุทธิ ÷ 1.07 (1,420.56), ภาษี = ยอดสุทธิ − ราคาก่อนภาษี (99.44), ผลรวม 2 ค่านี้ต้อง = ยอดสุทธิเป๊ะ ไม่มีเศษสตางค์หาย
- **TC-CARTPRICE-008** (Medium): ลำดับการแสดงผล Summary ท้ายบิลต้องเรียง: ราคารวม → ส่วนลดโปรโมชั่น → คูปองส่วนลด → ค่าส่ง → ราคาก่อนภาษี → ภาษี → ยอดสุทธิ (เช็คตำแหน่ง DOM/ลำดับบนจอจริง ไม่ใช่แค่ค่าตัวเลข)
- **TC-CARTPRICE-009** (High): ลบคูปองออก (กดถังขยะข้างรายการคูปอง) → คำนวณใหม่ทันที ยอดสุทธิเพิ่มขึ้นตามค่าคูปองที่ถูกลบ (กลับไปเป็น 1,620.00) ทุก field re-calculate ถูกต้อง
- **TC-CARTPRICE-010** (High): แก้จำนวนสินค้า (+/-) จากหน้าตะกร้า → ราคาทุกชั้น (รายบรรทัด + ราคาหลังลดต่อบรรทัด + Summary ทั้งหมด) คำนวณใหม่ถูกต้องตามลำดับเดิมทั้งหมด
- **TC-CARTPRICE-011** (Medium, Edge): ไม่มี Promotion/Coupon เลย (สินค้าไม่มีส่วนลดรายตัวด้วย) → ราคาหลังลดต่อบรรทัด = ราคารวมเฉยๆ (ไม่มี allocation ผิดพลาด), Summary แสดง "ส่วนลดโปรโมชั่น"/"คูปองส่วนลด" เป็น 0.00 หรือซ่อนแถวไปเลย (⚠️ ต้องยืนยัน design จริงกับ Dev/PM ก่อน)
- **TC-CARTPRICE-012** (Medium, Edge): จำนวนบรรทัด/มูลค่าที่หารสัดส่วนไม่ลงตัว (เช่น 3 บรรทัดราคาไม่เท่ากัน) → ตรวจว่าการปัดเศษต่อบรรทัดไม่ทำให้ Σ ราคาหลังลด ≠ ยอดสุทธิ (ต้องมี logic เผื่อเศษสตางค์ไปลงบรรทัดใดบรรทัดหนึ่ง ไม่ปล่อยหายไปเฉยๆ)
- **TC-CARTPRICE-013** (High): Order-level % Discount — PROMO-B-001 "ลดออเดอร์ 5% เมื่อครบ 1,000.-" (ซื้อครบ 1,000 บาท ลด 5%) และ PROMO-B-002 "ลดออเดอร์ 8% เมื่อครบ 3,000.-" (ซื้อครบ 3,000 บาท ลด 8%) — ตรวจว่าคำนวณ % จากยอดหลังหักส่วนลดรายตัวถูกต้อง (ตาม logic หัวข้อ 12.1) ทั้ง 2 threshold แยกกัน และไม่ลดซ้อนกันถ้าเข้าเงื่อนไขทั้งคู่พร้อมกัน (ต้องยืนยัน priority กับ Dev ว่าใช้ threshold สูงสุดที่เข้าเงื่อนไข หรือใช้ตัวแรก)
- **TC-CARTPRICE-014** (High): Order-level Discount บาท — PROMO-B-003 "ลดออเดอร์ 50 บาท เมื่อครบ 1,000.-" และ PROMO-B-004 "ลดออเดอร์ 200 บาท เมื่อครบ 3,000.-" — ตรวจว่าลดเป็นจำนวนเงินตายตัว (ไม่ใช่ %) ถูกต้อง และยอดต่ำกว่า threshold ต้องไม่ได้รับส่วนลด
- **TC-CARTPRICE-015** (High): Order-level แถมสินค้า — PROMO-B-005 "แถม COOL BABY เมื่อครบ 1,500.-" (แถม COOL BABY 3ซอง PCO01126 x1) และ PROMO-B-006 "แถม CUTINOVA HYDRO เมื่อครบ 2,500.-" (แถม CUTINOVA HYDRO 15x20CM. PCO01208 x1) — ตรวจว่าสินค้าแถมถูกเพิ่มเข้าตะกร้า/บิลอัตโนมัติ ราคา 0.00 ไม่นับรวมในยอดที่ต้องชำระ แต่แสดงในรายการสินค้า

- **TC-CARTPRICE-019** (Critical, Edge): Product Combination — PROMO-B-013 "แถม ACCU-CHEK ADVANTAGE เมื่อซื้อคละกลุ่ม ACCU-CHEK ครบยอด+จำนวน" (ซื้อคละกลุ่ม PCO00094/95/96/97 รวมกันครบ 10 ชิ้น **และ** ยอดรวมขั้นต่ำ 4,000 บาท **และ** ต้องมี PCO00094 อย่างน้อย 1 ชิ้นเป็น Mandatory item → แถม ACCU-CHEK ADVANTAGE 50'S.+เข็ม PCO00099 x1) — เป็นเคสซับซ้อนที่สุด ต้องทดสอบครบทุก combination: (ก) ครบเงื่อนไขทั้ง 3 ข้อ → ได้รับแถม, (ข) ครบจำนวน+ยอดเงินแต่ไม่มี PCO00094 (Mandatory) เลย → **ไม่ได้รับแถม**, (ค) มี PCO00094 + ครบยอดเงินแต่จำนวนรวมไม่ถึง 10 ชิ้น → ไม่ได้รับแถม, (ง) มี PCO00094 + ครบจำนวนแต่ยอดเงินไม่ถึง 4,000 → ไม่ได้รับแถม

- **TC-CARTPRICE-021** (Critical, Edge): ใช้ Promotion + Coupon พร้อมกัน — เข้าเงื่อนไข Order-level promotion (เช่น PROMO-B-001) พร้อมใส่ coupon `REGULAR_PRICE_10_PC` ในตะกร้าเดียวกัน → ตรวจลำดับการหักตาม logic หัวข้อ 12.1 (รายตัว → Promotion → Coupon → VAT) ว่า Coupon หักจากยอดหลัง Promotion เสมอ ไม่ใช่คิดจากยอดรวมดิบ, และ Summary "ส่วนลดโปรโมชั่น"/"คูปองส่วนลด" แยกบรรทัดถูกต้องตามหัวข้อ 12.1

#### 12.7.1 web-app: ตะกร้าสินค้า (Cart) — `/cart` (เพิ่มเติมจาก TC-CARTPRICE-001–014)

> ⚠️ **ขอบเขตใหม่อีกชั้น**: ผู้ใช้ระบุชัดว่า **"ไม่ได้ต้องตรวจสอบเฉพาะหน้าตะกร้า (Cart) เท่านั้น แต่ต้องตรวจสอบข้อมูลและสถานะของรายการแบบ End-to-End ทั้งฝั่ง User และ Admin"** — ต่างจากหัวข้อ 12 ที่เน้นความถูกต้องของ "ตัวเลขราคา" หัวข้อนี้เน้น **Flow ทั้งกระบวนการซื้อ + สถานะ + ความสอดคล้องของข้อมูลข้าม 8+ หน้าจอ**

### 13.1 Flow หลักที่ต้องทดสอบ (ตามที่ผู้ใช้ระบุ)

```
เลือกสินค้า → เพิ่มลงตะกร้า → ตรวจข้อมูลในตะกร้า → เลือกสินค้าที่จะซื้อ/เลือกทั้งหมด
   → กดชำระเงิน → ตรวจหน้าชำระเงิน → เลือกช่องทางชำระเงิน → ดำเนินการชำระเงินตามประเภท
   → ตรวจสถานะ+ข้อมูลใน "การซื้อของฉัน" → ตรวจข้อมูลฝั่ง Admin
   → ตรวจความสัมพันธ์ Cart → Payment → Order ตลอดสาย
```

### 13.3 Business Rule สำคัญ — พฤติกรรมต่างกันตามช่องทางชำระเงิน (ยืนยันจากผู้ใช้ + ทดสอบจริงแล้วสำหรับ Bank Transfer)

| ช่องทาง | หลังชำระ/ส่งหลักฐาน | สถานะ Order | Order ถูกสร้างเมื่อไหร่ |
|---|---|---|---|
| **QR Code** | ชำระสำเร็จทันที | ชำระเงินแล้ว | ทันทีหลังชำระสำเร็จ |
| **Credit Card** | ชำระสำเร็จทันที | ชำระเงินแล้ว | ทันทีหลังชำระสำเร็จ |
| **Bank Transfer** | รายการ**ยังอยู่ใน Cart list** สถานะ**รอตรวจสอบ** | (ยังไม่ปรากฏใน Order Management) | **เฉพาะหลัง Admin ปรับสถานะเป็น "ชำระเงินแล้ว"** เท่านั้น — ✅ **ทดสอบจริงแล้ว end-to-end 2026-09-09** (ดู 13.7.6) |

> ⚠️ **ข้อสังเกตใหม่จากการทดสอบจริง**: เลขที่ Order (เช่น `OR-260909-0261`) จริงๆ ถูก**จองไว้ล่วงหน้าตั้งแต่หน้า Payment**ก่อนชำระเงินเสร็จด้วยซ้ำ (เห็นค่า "เลขที่ใบสั่งซื้อ" บนหน้า `/payment` ตั้งแต่ก่อนกด "ส่งหลักฐานการโอน") แต่เลขที่นี้จะ**ไม่ปรากฏใน Order Management List** (ทั้ง User และ Admin) จนกว่า Admin จะ approve — ดังนั้น business rule ที่แม่นยำกว่าคือ "Order ถูกจองเลขที่ไว้ล่วงหน้า แต่ยังไม่ถูก 'สร้าง/เปิดเผย' ใน Order Management จนกว่าจะชำระเงินสำเร็จ" ไม่ใช่ "ยังไม่มี Order เลย" — ควรระบุ test assertion ให้ตรงจุดนี้ (เช็คว่า **ไม่ปรากฏในหน้า Order List** ไม่ใช่เช็คว่า "เลขที่ยังไม่ถูกสร้าง")

**🔴 Bank Transfer คือช่องทางที่ซับซ้อนที่สุดและมีความเสี่ยงสูงสุด** — ต้องทดสอบ 2 checkpoint แยกกันชัดเจน:
1. **ก่อน Admin Approve**: Cart ยังมีรายการ, สถานะ "รอตรวจสอบ", ยังไม่มี/ไม่แสดง Order, ข้อมูลการชำระเงิน+สลิปถูกต้อง
2. **หลัง Admin ปรับเป็น "ชำระเงินแล้ว"**: Cart อัปเดตตาม flow, Order ถูกสร้างสำเร็จ สถานะ "ชำระเงินแล้ว", ข้อมูลสินค้า/จำนวนเงิน/ยอดรวมถูกต้อง, ข้อมูลตรงกันระหว่าง User ↔ Admin

### 13.4 Test Scenarios

> ✅ = ทดสอบจริงบน staging สำเร็จแล้ว (2026-09-09, ดูหลักฐานหัวข้อ 13.7) พร้อม selector จริงสำหรับเขียน automation — ที่เหลือยัง manual/รอ open item

#### 13.4.1 Cart & Selection (ก่อนชำระเงิน) — หน้า `/companies/marketplace/cart`
- **TC-E2E-CART-001** (Critical) ✅: เปิดตะกร้า Shopping → ตรวจรายการสินค้า/จำนวน/ราคา/ส่วนลด/ยอดรวม/สถานะรายการครบก่อนชำระเงิน + Summary 7 field ครบ
- **TC-E2E-CART-002** (High) ✅: เลือกเฉพาะร้านค้าเดียว (ไม่ใช่ "checkbox รายตัว" ตามที่เข้าใจตอนแรก) แล้วกด "ชำระเงิน" → เฉพาะสินค้าของร้านที่เลือกเท่านั้นที่ไปปรากฏในหน้าชำระเงิน — ⚠️ **แก้จากที่เข้าใจผิดตอนแรก**: ตะกร้าไม่มี checkbox เลือกสินค้ารายตัว มีแค่ checkbox ระดับ "ร้านค้า" (seller group) อยู่ใน `<thead><tr><th>` ของแต่ละ mini-table ต่อร้าน (พบจริงตอนเขียน automation)
- **TC-E2E-CART-003** (High) ✅: กด checkbox exact-text **"เลือกซื้อรายการสินค้า (เลือกทั้งหมด)"** → กด "ชำระเงิน" → ครบทุกรายการในหน้าชำระเงิน — ⚠️ **selector trap**: `input[type=checkbox]` ตัวแรกบนหน้าคือช่อง "ที่อยู่ในการออกใบกำกับภาษี" (คนละตัว) ต้องหาด้วย exact-text label แล้ว XPath `preceding-sibling::input` เท่านั้น

#### 13.4.2 Payment Page — หน้า `/companies/marketplace/payment`
- **TC-E2E-PAYMENT-001** (Critical) ✅: ข้อมูลสินค้าที่เลือกมาจากตะกร้าถูกต้องครบในหน้าชำระเงิน ยอดรวมสุทธิตรงกับหน้าตะกร้าเป๊ะ — พบ stepper 3 step (**รอการชำระ → ตรวจสอบสถานะ → ชำระเรียบร้อย**) และ "เลขที่ใบสั่งซื้อ" ถูกจองแสดงไว้ตั้งแต่ก่อนชำระเงินเสร็จ (ดูหมายเหตุ 13.3) ไม่มีข้อมูลสูญหาย/เปลี่ยนแปลงระหว่าง Cart → Payment

#### 13.4.3 Bank Transfer — Flow เต็ม (ทดสอบจริงครบทุกเคสแล้ว)
- **TC-E2E-BANK-001** (Critical) ✅: เลือกแท็บ "โอนผ่านธนาคาร" (คลิกด้วยข้อความ ไม่ใช่ radio) → กด "แนบหลักฐานการโอน" → กรอกวันที่ (`input[placeholder="วว/ดด/ปปปป"]`) → กรอกเวลา (`input[placeholder="00"]` ×2 ช่องแยกชม./นาที) → กรอกจำนวนเงิน (`input[placeholder="0.00"]`) → อัพโหลดไฟล์ (`input[type=file]`, accept .jpeg/.jpg/.png) → กด "ตกลง" ในโมดัล → ติ๊ก checkbox ยอมรับ → กด "ส่งหลักฐานการโอน" → ทุกฟิลด์บันทึกถูกต้องครบ ไม่มี error, หน้าเปลี่ยนเป็น "คำสั่งซื้ออยู่ระหว่างตรวจสอบ"
- **TC-E2E-BANK-002** (Critical, High Priority ตามผู้ใช้) ✅: **ก่อน Admin Approve** — Cart list ทั้ง User (`/order-management/cart`) และ Admin (`/arinlink/order-management/cart?page=1`) แสดงสถานะ "รอตรวจสอบ" ตรงกัน 100% (Ref No./ราคารวม/ผู้ซื้อ) และ Admin Order List **ยังไม่มี** Order ปรากฏเลยตามคาด
- **TC-E2E-BANK-003** (Critical, High Priority ตามผู้ใช้) ✅: **Admin เปลี่ยนสถานะ** — คลิก `.dropdown-toggle` ของแถวใน Admin Cart list → เลือก "ชำระเงินเเล้ว" (⚠️ DB สะกดซ้ำ เ 2 ตัว ใช้ partial-text match) → modal "เปลี่ยนสถานะการชำระเงิน" เปิดขึ้น → **ต้องกรอกช่อง "หมายเหตุ" (textarea, required)** ก่อนกด "บันทึก" (ไม่งั้นปุ่มจะไม่ทำงานแบบไม่มี error แจ้ง) → Cart status เปลี่ยนเป็น "ชำระเงินแล้ว" ทันที → Order ปรากฏใน Order List **ทันที** (สถานะออเดอร์="รับออเดอร์แล้ว", สถานะการชำระ="ชำระเงินแล้ว") ตรงกันทั้ง User Order และ Admin Order
- **TC-E2E-BANK-004** (High, High Priority ตามผู้ใช้) ✅: เทียบ snapshot ก่อน-หลัง Admin เปลี่ยนสถานะแบบ field-by-field — ทุก field เปลี่ยนพร้อมกันสอดคล้องกัน ไม่มี field ไหนค้างสถานะเก่า

#### 13.4.4 QR Code Payment
- **TC-E2E-QR-001** (Critical, High Priority ตามผู้ใช้) ⏸️: ชำระผ่าน QR Code สำเร็จ → ระบบสร้าง Order ทันที สถานะ "ชำระเงินแล้ว" → ตรวจข้อมูล Order ทั้งฝั่ง User (My Purchase → Order) และ Admin (Admin Order) — **ยังทดสอบจริงไม่ได้**: ต้องมี sandbox/mock payment gateway บน staging (Open Item ค้าง ดู 13.6) แท็บ "สแกน QR" บนหน้า Payment สำรวจ selector ไว้แล้ว (ปุ่ม `button:has-text("สแกน QR Code")`)

**Bug/pitfall ใหม่ที่เจอตอนเขียน automation จริง (นอกเหนือจากหัวข้อ 13.7):**
- 🔴 **ช่องเวลา (ชม./นาที) ในโมดัลแนบหลักฐานมี `minlength="2"` (native HTML5 validation)** — ถ้ากรอกเลขตัวเดียว (เช่น `"0"` แทน `"00"`) ปุ่ม "ตกลง" จะดูเหมือนกดได้ปกติแต่ browser บล็อกการปิด modal เงียบๆ ด้วย tooltip "Please lengthen this text to 2 characters" ทำให้ modal ค้าง intercept ปุ่มอื่นทั้งหน้าต่อเนื่อง (อาการเหมือน bug modal-ไม่ปิดที่เคยเจอในหัวข้อ 11 แต่ root cause คนละอันกัน) — แก้ด้วยการ `padStart(2, '0')` ให้ชม./นาทีเสมอ
- ต้องรวม TC-E2E-CART-003/PAYMENT-001/BANK-001 เป็น **test เดียวกัน** (ไม่แยก `test()`) เพราะแต่ละ `test()` ได้ `page`/context ใหม่ — ถ้าแยกจะได้เลขที่ใบสั่งซื้อคนละใบต่อเทส ทำให้เทสถัดไปตรวจสอบผิดรายการ
- ใช้ `fixtures/test-image.jpg` ที่มีอยู่แล้วในโปรเจกต์เป็นไฟล์สลิปแนบ (portable ข้ามเครื่อง แทนการอ้าง path ใน `~/Downloads/` ที่ใช้ตอน discovery)
- 🔴 **หน้า Admin Cart Detail ไม่มีตาราง Summary เหมือนที่สันนิษฐานไว้ตอนแรก** (มีแค่ "ยอดรวม" เฉยๆ) — เจอตอน assertion แรกที่เขียนพัง ต้องกลับไปดู screenshot จริงแล้วแก้ assertion ให้ตรงโครงสร้างจริง (บันทึกไว้ในหัวข้อ 13.7.5 แล้ว)
- 🔴 **หา status dropdown บนหน้า Order Detail ด้วย `hasText` แบบกว้างไม่ได้** — `page.locator('div').filter({hasText:'สถานะชำระเงิน :'})` จับ div ครอบทั้งหน้าแล้วเจอ `.dropdown-toggle` ตัวแรกที่ไม่ใช่ตัวที่ต้องการ (ดันไปโดน filter dropdown "Select..." แถบซ้ายแทน) ต้องใช้ exact-text label + XPath `following-sibling::div[1]//button[...]` เหมือน pattern checkbox ที่ใช้อยู่แล้ว
- 🔴 **ตะกร้าไม่มี checkbox เลือกสินค้ารายตัว — เลือกได้แค่ระดับร้านค้า (seller group)** เท่านั้น สินค้าแต่ละชิ้นถูกจัดกลุ่มเป็น mini-table แยกตามร้าน checkbox อยู่ใน `<thead><tr><th>` ของแต่ละ mini-table (ไม่ใช่ต่อแถวสินค้า) — ค้นพบตอนเขียน TC-E2E-CART-002 ที่ตั้งใจทดสอบ "เลือกสินค้าบางส่วน" ต้องแก้ premise ของเคสให้ตรง UI จริง (ใช้สินค้า 2 ชิ้นจาก 2 ร้านต่างกันแทน)
